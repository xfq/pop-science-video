# 视觉语法

计算机概念大多“看不见”。视觉的任务不是装饰，而是把不可见的结构变成可追踪的图形：**谁在动、经过哪一步、在哪一刻发生了变化。**

## 先选信息形态，再选颜色

| 概念的结构 | 用哪种画面 | 不要用 |
| --- | --- | --- |
| 有先后/因果的步骤 | 流程条（pipeline） | 环形图、无方向的粒子 |
| 固定位宽/编码/字节 | 位字段（bitfield）、字节格 | 抽象网格、随机代码雨 |
| 层次/缓存/协议栈 | 层叠条（layers） | 3D 透视塔（会误导比例） |
| 两个选项/误区/权衡 | 对照卡（compare） | 只放两个 Logo |
| 数量级/误差/尺度 | 数字卡（numbers）、数轴 | 没有刻度的柱状图 |
| 可执行的真相 | 终端/代码（code） | 手绘伪代码、模糊截图 |
| 一句话结论 | 纸张大字（statement） | 满屏特效 |
| 回顾/规则 | 清单（recap） | 再讲一遍机制 |
| 留问题/下期 | 大字问题（outro） | 突然黑屏 |

### 一个判断方法

问自己：**如果关掉旁白，观众能从画面上看出“什么导致了什么”吗？**

- 看不出 → 画面只是壁纸，换成流程图/位字段/对照。
- 看得出但方向错了 → 箭头、时间轴、顺序需要重画。
- 看得出但比例错了 → 加刻度/标注，或明确写“示意”。

## 模板里的 10 种镜头

所有镜头都由 `film.json` 驱动，`build.mjs` 生成对应的 sub-composition。字段如下。

### 1. `hook` 开场冲突

```json
{
  "type": "hook", "kicker": "一个每天都在发生的怪事",
  "a": "0.1", "b": "0.2", "result": "0.30000000000000004",
  "note": "这不是 bug。",
  "bits": "001111...1010", "hex": "0x3FB999999999999A"
}
```

- 左侧大表达式 + 结果；右侧可选 64 位“内存转储”。
- 第 1 帧必须完整：标题、表达式、结果都在。**不要**把结果做成 3 秒后才出现的 reveal。
- 只放一个冲突；不要在 hook 里解释机制。

### 2. `statement` 结论/转折

```json
{"type":"statement","tag":"THE PIVOT","line1":"不是 bug。","line2":"是二进制。","sub":"所有遵循 IEEE 754 的语言，都会给出同一个答案。","index":"01 — 问题的形状"}
```

- 暖白纸张卡片 + 两行大字；一行结论，一行纠正。
- 适合放在 hook 之后，把“吐槽”转成“机制”。
- `sub` 只放一句限定/证据，不要写成第二段旁白。

### 3. `pipeline` 流程/因果

```json
{"type":"pipeline","title":"0.1 是怎么变成“近似值”的？","steps":[
  {"label":"0.1","sub":"十进制输入","note":"看起来是精确的"},
  {"label":"0.000110011…","sub":"二进制展开","note":"0011 无限循环"},
  {"label":"53 位","sub":"截断 + 舍入","note":"存进 binary64"}
],"foot":"误差从输入就开始了。"}
```

- 3–6 步；每步一个动词/状态；箭头方向必须等于因果方向。
- 卡片里只放一个核心值 + 一句解释；不要把整段旁白塞进去。
- 最后一步用 `tone:"amber"` 标结果；其他步骤保持中性。
- 步数 > 6 时拆成两镜，或改成 `layers`。

### 4. `bitfield` 编码/位宽

```json
{"type":"bitfield","title":"64 位里，只有 53 位存有效数字","segments":[
  {"label":"符号","bits":1,"tone":"amber","note":"0 正 / 1 负"},
  {"label":"指数","bits":11,"tone":"cyan","note":"偏置 1023"},
  {"label":"尾数","bits":52,"tone":"blue","note":"隐含最高位 1"}
],"bits":"001111...1010","hex":"0x3FB999999999999A"}
```

- 用真实比例画位宽；1 位的段太窄时，标签放到下面的图例，不要把宽度硬拉大。
- 位串按 4 位分组，颜色对应字段；必须和实际值一致（用 `struct` / `hex()` 核过）。
- 说明“隐含位”“偏置”“subnormal”等例外，否则观众会把简化当全部。

### 5. `code` 真实验证

```json
{"type":"code","titleLines":["存进去的 0.1，","已经不是 0.1。"],"lang":"python3",
 "lines":[
   {"text":">>> (0.1).hex()","tone":"in"},
   {"text":"'0x1.999999999999ap-4'","tone":"str"},
   {"text":">>> 0.1 + 0.2","tone":"in"},
   {"text":"0.30000000000000004","tone":"out"}
 ],
 "note":"十六进制里，0.1 的尾数已经是一串近似值。"}
```

- `tone`: `in` 输入、`out` 输出、`str` 字符串、`err` 错误/False、`comment` 注释、`dim` 次要。
- 最多 8–10 行；超过就拆镜，或只留关键 3 行。
- 代码必须能跑；输出必须实际运行。可以用 `>>>` 表示交互，但不要伪造。
- 右侧的 `note` 只解释“这段输出意味着什么”，不要重复代码。

### 6. `compare` 对照/误区

```json
{"type":"compare","title":"同一个 0.3，两个不同的数",
 "left":{"tag":"MATHEMATICS","title":"精确的 0.3","value":"3 / 10","note":"无限精度"},
 "right":{"tag":"BINARY64","title":"存储的 0.3","value":"0.2999999999999889…","note":"53 位以内"},
 "verdict":"它们相差约 1.1e-17。"}
```

- 左边放“直觉/数学/旧做法”，右边放“机器/新做法/真实值”。
- 中间的 `VS` 只做分隔，不要做成两个品牌 Logo 对战。
- `verdict` 要给一个可验证的结论，不要只说“不一样”。

### 7. `numbers` 尺度/误差

```json
{"type":"numbers","title":"53 位，大约 16 位十进制","stats":[
  {"value":"53","unit":"位","label":"有效二进制数字","note":"1 符号 + 11 指数 + 52 尾数","tone":"cyan"},
  {"value":"16","unit":"位","label":"十进制有效数字","note":"约 15–17 位，取决于具体数值"},
  {"value":"1","unit":"ulp","label":"与 0.3 的差","note":"ulp = 最后一位的 1 个单位"}
],"equation":"0.30000000000000004 − 0.3 = 5.551115123125783e-17"}
```

- 一张卡只放一个数；单位必须可见；比较量级时用同一口径。
- `equation` 放可复算的算式，比“误差很小”有说服力。
- 不要把“1 ulp”说成“1 个字节”或“1 个最小单位”而不解释。

### 8. `layers` 层次/权衡

```json
{"type":"layers","title":"每一层都在用时间换空间","layers":[
  {"label":"寄存器","sub":"REGISTER","pct":2,"tone":"amber","note":"~1 个周期"},
  {"label":"L1 缓存","sub":"L1 CACHE","pct":6,"tone":"amber","note":"~4 个周期"},
  {"label":"内存","sub":"DRAM","pct":100,"tone":"blue","note":"~200 个周期"}
],"foot":"数字是数量级示意，不同 CPU 差异很大。"}
```

- `pct` 是视觉长度，不一定是真实线性比例；如果用了非线性，`foot` 必须写“示意/对数”。
- 层数 ≤ 6；每层只放名称、一个数字、一个备注。
- 不要用 3D 塔/透视来暗示高度 = 性能；会用错。

### 9. `recap` 规则/清单

```json
{"type":"recap","title":"下次写代码，记住这三条","items":[
  {"n":"01","title":"比较小数，别用等号","note":"用 math.isclose(a, b)，或者自己给一个容差。","code":"math.isclose(a, b)"}
],"foot":"浮点适合科学计算，不适合精确账本。"}
```

- 三条以内；每条一个动作 + 一个代码/判断。
- 不要在 recap 引入新概念；只收束前面已经解释过的内容。

### 10. `outro` 留问题/下期

```json
{"type":"outro","questionLines":["那 0.1 在内存里，","到底长什么样？"],"next":"下一期 · 拆开 64 个格子","teaser":"float.hex(0.1)","teaserValue":"0x1.999999999999ap-4","sources":["IEEE 754-2019","Goldberg 1991","Python Docs"]}
```

- 问题要具体，能自然接下一期；不要“所以我们下期再见”。
- 来源放在底部；如果平台会裁切，确保安全区内。
- 结尾至少停 0.5 秒再黑屏，不要把最后一帧切掉。

## 版式规则

- 1920×1080：左右安全边距 120px；顶部 52–156px；正文底线 900px；字幕底部 48px；页脚在 154px，避免和字幕重叠。
- 标题 62–96px，正文 24–33px，代码 27px，页脚 21px，字幕 33px。**1080p 下正文不要小于 24px。**
- 每镜一个主张；标题最多两行；正文最多三行；代码最多 8 行。
- 图表最多 7 个节点；超过就分组或拆镜。
- 箭头只表示因果/时间/数据流；不要用箭头做装饰。
- 所有数字带单位；所有坐标轴有刻度和起止值；不按比例时写“示意”。

## 色彩语义

| 颜色 | 含义 | 用法 |
| --- | --- | --- |
| 青 `#5eead4` | 机制、正确路径、可表示 | 主线、关键步骤、成功 |
| 蓝 `#60a5fa` | 结构、存储、背景信息 | 位字段、层次、辅助节点 |
| 琥珀 `#fbbf24` | 结果、注意、差异 | 最终值、ulp、提醒 |
| 珊瑚 `#fb7185` | 错误、反例、失败 | False、报错、误区 |
| 绿 `#34d399` | 通过、确认 | isclose、True、完成 |

颜色不是唯一编码：同时用文字、图标、位置。不要让色盲观众丢失信息。

## 动效规则

- **只在旁白标记处揭示。** 画面动作为“说到”服务，不是为动而动。
- 入场 0.5–0.7 秒；同一镜不要所有元素都用同一种入场。
- 一镜最多一个持续运动（如背景漂移）；循环必须按镜头时长截断，不能无限。
- 不动的元素保持不动；不要让所有东西同时呼吸。
- 转场只在尺度/时间/空间变化时使用；硬切是默认。
- 首帧完整；如果必须做入场，从“完整画面”做轻微位移/透明度，不要从空白开始。

## 常见误导

| 误导 | 为什么错 | 改法 |
| --- | --- | --- |
| 位字段段宽按“重要性”而不是位数 | 观众会以为 1 位 = 52 位 | 按真实位数比例，或明确标“非比例” |
| 线性柱状图表示跨数量级数据 | 长度会骗人 | 对数轴/直接标数值 |
| 3D 透视图表示缓存层次 | 高度/面积被误读 | 用水平层叠条 + 数字 |
| 箭头从结果指向原因 | 因果反了 | 重画方向，箭头旁写动词 |
| 终端输出被“美化” | 观众无法复现 | 用真实输出，保留提示符/版本 |
| 用“数据流”粒子表示一切 | 没有信息量 | 换成具体节点/边/状态 |
| 把类比画成机制 | 观众记住类比，没记住机制 | 类比只做第一层，后面回到真实术语 |

## 镜头表模板

| # | 时间 | 画面类型 | 核心信息 | 旁白 mark | 事实 id |
| --- | --- | --- | --- | --- | --- |
| 1 | 0–12s | hook | 真实输出 0.30000000000000004 | `result` | c1 |
| 2 | 12–21s | statement | 不是 bug，是二进制 | `line1` | c1 |
| 3 | 21–36s | pipeline | 输入 → 53 位 → 相加 → 结果 | `s0`–`s4` | c2, c3 |

镜头表写到“每一秒”不现实；写到“每句话落在哪个 mark”就够了。时间由 TTS 实测后回填。
