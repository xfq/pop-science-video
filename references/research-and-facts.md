# 研究与事实

科普片的第一现场不是剪辑软件，而是事实台账。画面可以重做，错误一旦发出去就收不回来。

## 来源等级

| 等级 | 例子 | 怎么用 |
| --- | --- | --- |
| A. 规范 / 标准 / 论文 / 官方文档 | IEEE 754、RFC、POSIX、语言官方文档、原始论文 | 可直接支撑主张；优先引用具体章节 |
| B. 教材 / 课程 / 权威机构 | 操作系统教材、MDN、CS50、NIST | 可支撑解释；注意版本和简化 |
| C. 高质量科普 / 工程博客 | Julia Evans、Brendan Gregg、厂商工程博客 | 用来找解释方式和例子；关键数字回查 A/B |
| D. 百科 | Wikipedia | 只当索引，不作为唯一来源 |
| E. 博客 / 视频 / 论坛 / LLM 输出 | 个人文章、Stack Overflow、模型回答 | 只当线索；必须回查 A/B 或实机验证 |

正式片至少两条 A 级来源。只有一个来源时，找第二条独立来源，或者把主张降级为“某文档这么说”。

**“独立”不等于“两个网页都这么写”。** 如果两篇都转述同一个博客，它们仍然是一个来源。

## 事实台账

`facts.json` 的每条 claim：

```json
{
  "id": "c1",
  "claim": "在 IEEE 754 binary64 中，0.1 + 0.2 的求值结果是 0.30000000000000004。",
  "status": "verified",
  "sources": [
    {"title": "Python 3 documentation", "url": "https://docs.python.org/3/tutorial/floatingpoint.html", "kind": "primary", "accessed": "2026-10-21"}
  ],
  "verification": "Python / Node / C / Java 实机运行，四者输出一致；记录在 evidence/verification.txt。",
  "caveat": "binary64 / double；binary32 的结果不同。"
}
```

字段要求：

- `status`：`verified`（已核对）/ `needs-review`（待核）/ `unverified`（未核）/ `opinion`（观点）。正式片只允许 verified；`check_content.py --strict` 会把待核当错误。
- `sources`：至少一条；`kind` 用 `primary` / `secondary` / `reference`。URL 必须能打开。
- `verification`：你**怎么**核的。实机运行、原文哪一节、谁复现过。不要写“网上都这么说”。
- `caveat`：适用版本、平台、前提、单位。没有边界的断言，通常就是过度断言。

`SOURCES.md` 是人读版本：一行一条，带访问日期和核验方式。两份文件不要互相矛盾。

## 代码与输出

代码是证据，不是装饰。

1. **跑真实代码。** 用片中将展示的同一语言、同一版本、同一表达式。把命令和输出保存到 `evidence/verification.txt`。
2. **不要手写终端。** 可以缩短提示符、换字号、隐藏无关行，但不能改输出。需要折行时标注 `↩`。
3. **补全上下文。** 片段要能独立运行：import、变量定义、版本。示例里的 `math.isclose` 要能看出 `import math`。
4. **区分“读取”和“打印”。** `0.1` 的屏幕显示是最短往返表示，不是内存里的精确值；要展示精确值时用 `hex()` / `Decimal` / 位模式，并说明这是另一种表示。
5. **版本会变。** 语言默认值、库行为、性能数字都可能变。页脚写版本；没有版本就不说“最新”。

本片的核验示例（真实输出见 `examples/float-0-1-0-2/evidence/verification.txt`）：

```text
Python 3.14: 0.1 + 0.2 -> 0.30000000000000004; == 0.3 -> False
Node 24: 同上
C (clang): printf("%.17g") -> 0.30000000000000004; == 0.3 -> 0
Java: 同上；Double.toHexString(0.1) -> 0x1.999999999999ap-4
```

一个容易讲错的细节：`0.1` 和 `0.2` 的存储值相加，精确和恰好落在两个相邻 double 的正中间；默认的 round-to-nearest, ties-to-even 选了上面那个。所以“相加再舍入一次”是真的，但这不是“随机误差”。如果片里要展开这一点，必须把 tie 讲清；不讲就把“再舍入一次”作为概略说法，并在台账 `caveat` 注明。

## 数字、单位与量级

- **单位写全。** `ms` / `µs` / `ns`、`MB` / `MiB`、`Mbps` / `MB/s`。1 KB 是 1000 还是 1024，取决于语境，必须说明。
- **区分延迟与带宽。** “更快”可能指延迟更低、吞吐更高、或首字节更早；三者不能互换。
- **不要假精确。** “约 200 个周期”比“200.0 个周期”诚实；不同 CPU 差异很大时，页脚写“数量级示意”。
- **图表要给尺度。** 线性轴/对数轴、起止值、采样口径。用条形图表示跨数量级数据时，优先对数轴或直接标数值，不要让长度暗示线性比例。
- **换算要可复算。** 53 位 ≈ 53 × log10(2) ≈ 15.95 位十进制；1 ulp near 0.3 = 2⁻⁵⁴ ≈ 5.55 × 10⁻¹⁷。把算式留在台账里。

## 时效与范围

- 价格、版本号、性能排名、法规、云服务限制都会过期；写访问日期，并在片中给时间限定。
- 基准测试写清硬件、编译器/运行时、负载、测量方法。没有这些，数字只能当轶事。
- 安全话题先写威胁模型：防谁、防什么、不防什么。没有威胁模型的“安全”是口号。
- 平台差异要说明：Linux/macOS/Windows、浏览器/Node、32/64 位、JIT/解释执行。

## 常见计算机误区（选题时先排查）

| 常见说法 | 更准确的说法 |
| --- | --- |
| “浮点数就是不准” | 可表示的值是精确的；十进制输入和运算结果会发生舍入。 |
| “0.1 在计算机里不存在” | 存的是一个最接近 0.1 的 binary64 值，误差约 5.55e-18。 |
| “用 Decimal 就无限精确” | Decimal 仍有上下文精度；它只是按十进制规则舍入。 |
| “多线程一定更快” | 取决于并行度、锁、内存带宽和 Amdahl 限制；可能更慢。 |
| “HTTPS 加密了整个网页” | TLS 保护传输；页面内容、资源、元数据、终端仍可能有别的暴露面。 |
| “删文件就是抹掉数据” | 通常只是解除索引；数据可能留在磁盘/备份/日志里。 |
| “缓存一定提高性能” | 命中率、失效、冷启动、一致性都可能让缓存变慢或变复杂。 |
| “32 位/64 位只是数字大小” | 影响地址空间、指针宽度、ABI、默认类型和对齐。 |
| “算法复杂度低就一定快” | 常数、缓存局部性、输入分布、实现质量同样重要。 |
| “AI 生成的解释可以直接用” | 模型会编造 API、版本和数字；必须回查文档或实机。 |

这张表不是要逐条讲，而是写片前用来检查：你的脚本有没有踩到其中一条？

## 类比的边界

每个类比至少写三行：

```json
{
  "text": "像一把刻度固定的小数尺",
  "maps": "尾数只有 52 位存储位，加上隐含的 1 共 53 位有效数字",
  "breaks": "浮点数不是固定小数点：指数会让刻度的绝对间距随数量级变化"
}
```

没有 `breaks` 的类比，`check_content.py` 会报错。类比只能帮助建立第一层直觉，不能替代机制；在关键结论处要回到真实术语和数字。
